# Hyprland Configuration Integration Guide

**Last Updated**: 18/08/2026
**Version**: 1.0.0
**Maintained By**: Development Team
**Language**: British English (en_GB)
**Timezone**: Europe/London

---
This document explains how the modular Hyprland Lua configs in `config/hypr/`
integrate with the NixOS Home Manager configuration.

## Current Setup

The configuration is split across two layers:

| Layer | File | Responsibility |
|-------|------|----------------|
| NixOS | `modules/desktop/hyprland/default.nix` | The Hyprland package, `programs.hyprland.enable`, greetd/tuigreet session, XDG portals, ecosystem packages |
| Home Manager | `home/modules/hyprland.nix` | User-level Hyprland config (Lua files), plus waybar, wofi, hyprpaper, hypridle, hyprlock |

Home Manager owns the config *content*; the NixOS module owns the *package and
session*. `home/modules/hyprland.nix` deliberately sets `package = null` and
`portalPackage = null` so Home Manager does not install a second Hyprland and
duplicate the systemd units the NixOS module already provides. `systemd.enable =
false` is set for the same reason.

### The Lua config provider

Hyprland 0.56 supports two config providers, and Home Manager exposes the choice
as `wayland.windowManager.hyprland.configType`:

- `"hyprlang"` → Home Manager writes `~/.config/hypr/hyprland.conf`
- `"lua"` → Home Manager writes `~/.config/hypr/hyprland.lua`

This repository sets `configType = "lua"`.

```nix
wayland.windowManager.hyprland = {
  enable = true;
  configType = "lua";
  package = null;
  portalPackage = null;
  systemd.enable = false;

  extraLuaFiles = {
    "00-vars" = { content = ../../config/hypr/00-vars.lua; autoLoad = false; };
    "10-base" = ../../config/hypr/10-base.lua;
    # … 20-monitors … 80-autostart
  };
};
```

Check which provider a running session actually picked with:

```bash
hyprctl status   # prints e.g. `configProvider: lua`
```

### How the files get deployed

`extraLuaFiles` is an attrset of *module name* → file. Home Manager:

1. Writes each entry to `$XDG_CONFIG_HOME/hypr/<name>.lua` (dots in the name
   become directories, so `"ui.bindings"` would land at `hypr/ui/bindings.lua`).
2. Generates `$XDG_CONFIG_HOME/hypr/hyprland.lua`, which prepends
   `~/.config/hypr` to Lua's `package.path` and then emits one `require()` per
   entry that has `autoLoad = true`.

The generated entry point looks like this:

```lua
-- Generated by Home Manager.
local hm_xdg_config_home = os.getenv("XDG_CONFIG_HOME") or "/home/<user>/.config"
package.path = hm_xdg_config_home .. "/hypr/?.lua;" .. hm_xdg_config_home .. "/hypr/?/init.lua;" .. package.path

require("10-base")
require("20-monitors")
…
require("90-device")
```

You cannot define an entry called `hyprland.lua` — Home Manager generates that
file itself. The old `config/hypr/hyprland.conf` "source = …" manifest therefore
has no successor and has been retired.

**Load order** is alphabetical on the attribute name, so the numeric prefixes are
load-bearing: `10-` … `80-` for the shared files, `90-device` for the per-device
override that must win. See `README.md` for the full explanation.

**`00-vars` is `autoLoad = false`.** It is a Lua *module* that returns a table
(the `$mod` replacement), pulled in with `require("00-vars")` by the files that
need it. Auto-requiring it at top level would do nothing useful.

## Current File Mapping

| Lua file | Hyprland API used | Replaces |
|----------|-------------------|----------|
| `00-vars.lua` | plain Lua table | `$mod = SUPER` |
| `10-base.lua` | `hl.env`, `hl.config({ general, dwindle, master, misc, debug })` | `base.conf` |
| `20-monitors.lua` | `hl.monitor` | `monitors.conf` |
| `30-input.lua` | `hl.config({ input, xwayland })` | `input.conf` |
| `40-appearance.lua` | `hl.config({ decoration })` | `appearance.conf` |
| `50-animations.lua` | `hl.config({ animations })`, `hl.curve`, `hl.animation` | `animations.conf` |
| `60-keybinds.lua` | `hl.bind` + `hl.dsp.*` | `keybinds.conf` |
| `70-windowrules.lua` | `hl.window_rule` | `windowrules.conf` |
| `80-autostart.lua` | `hl.on("hyprland.start", …)` + `hl.exec_cmd` | `autostart.conf` (`exec-once`) |
| `devices/*.lua` | any of the above | `devices/*.conf` |

## Device-Specific Settings

Each device's Home Manager file registers its own `90-device` entry rather than
dropping a file with `home.file`. This matters: a plain `home.file` copy would
land in `~/.config/hypr` but would never be `require()`d, so the overrides would
silently do nothing.

```nix
# home/laptop.nix (and laptop-desktop / -dev / -productivity / -creative)
wayland.windowManager.hyprland.extraLuaFiles."90-device" = {
  content = ../config/hypr/devices/laptop-intel.lua;
  autoLoad = true;
};
```

The same pattern applies to `home/framework*.nix` → `devices/framework.lua` and
`home/devtower*.nix` → `devices/devtower.lua`.

Because `90-device` sorts last, and `hl.config()` merges leaf keys rather than
replacing whole blocks, a device file can override a single setting (say
`decoration.blur.size`) without restating everything around it.

## Editor Support (`.luarc.json`)

Hyprland ships LuaLS stubs for the `hl.*` API at
`<hyprland-package>/share/hypr/stubs/`. Home Manager normally writes
`hypr/.luarc.json` pointing at them, but it guards that on `finalPackage != null`
— and this repository deliberately sets `package = null`. `home/modules/hyprland.nix`
therefore writes the equivalent `.luarc.json` itself, sourcing the stubs from the
Hyprland package that the NixOS module installs:

```nix
xdg.configFile."hypr/.luarc.json" = lib.mkIf (osConfig != null) {
  text = builtins.toJSON {
    workspace.library = [ "${osConfig.programs.hyprland.finalPackage}/share/hypr/stubs" ];
    diagnostics.globals = [ "hl" ];
  };
};
```

## Runtime Control (`hyprctl`)

The Lua provider changes what `hyprctl` accepts. This is the part most likely to
break scripts written for the hyprlang era:

| Task | hyprlang era | Lua provider |
|------|--------------|--------------|
| Set a config value at runtime | `hyprctl keyword general:border_size 10` | `hyprctl eval 'hl.config({ general = { border_size = 10 } })'` |
| Run a dispatcher | `hyprctl dispatch movefocus l` | `hyprctl dispatch "hl.dsp.focus({ direction = 'left' })"` |
| Turn displays on | `hyprctl dispatch dpms on` | `hyprctl dispatch "hl.dsp.dpms('on')"` |
| Reload the config | `hyprctl reload` | `hyprctl reload` (unchanged) |
| Query state | `hyprctl monitors` / `clients` / `devices` | unchanged |

`hyprctl keyword` is documented as not working under a Lua provider. `hyprctl
dispatch` still exists but its argument is now wrapped as `hl.dispatch(<text>)`,
so a bare legacy dispatcher name fails with:

```
error: 3 [string "return hl.dispatch(dpms on)"]:1: ')' expected near 'on'
 → Note: dispatch in lua is a shorthand for hl.dispatch(...), your syntax might need to be updated.
```

Anything in this repository that shells out to `hyprctl dispatch` with a legacy
dispatcher name needs updating to the Lua form.

## Testing Changes

### Syntax check before rebuilding

```bash
luac -p config/hypr/*.lua config/hypr/devices/*.lua
```

### Apply

```bash
sudo nixos-rebuild switch --flake ~/Repos/personal/nix-config#<host>
```

Note that Home Manager's automatic "reload Hyprland on config change" hook is
gated on `package != null`, and this repository sets `package = null`. Changes
therefore do not reload themselves — run `hyprctl reload` (or log out and back
in) after a rebuild.

### Legacy file cleanup

`home/modules/legacy-cleanup.nix` backs up and removes stale
`~/.config/hypr/*.conf` files from the hyprlang era. It deliberately does not
touch `.lua` files — those are the current, managed configuration.

## Rolling Back

The Lua provider is opt-in; hyprlang still works in Hyprland 0.56. To go back:

1. Set `configType = "hyprlang"` in `home/modules/hyprland.nix`.
2. `git revert` the migration commit to restore the `.conf` files and the
   `home.file.".config/hypr/device.conf"` device wiring.
3. Rebuild.
